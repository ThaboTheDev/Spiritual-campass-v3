# Assumptions and decisions

This file distinguishes implementation choices from items that need product, legal, or deployment confirmation. The latter must be resolved before a public release.

## Product data and privacy

1. **Centre directory is not present in the repository.** No centre names, addresses, regions, or coordinates were supplied. `supabase/seed/centres.csv` remains header-only, and the import workflow rejects anything other than an operator-supplied, approved 88-row file. The app shows an explicit empty state; it does not fabricate locations. A verified directory is a launch prerequisite.
2. **Privacy/support contact was not supplied.** `SUPPORT_EMAIL` is an optional public Flutter `--dart-define`. Without it, the membership view does not invent an address and instructs the operator to publish a monitored contact before launch.
3. **Retention and deletion:** account deletion removes the Supabase Auth user; database foreign keys cascade the member row and linked payment rows. Manual coordinates are stored only in local app preferences and are cleared by the delete-account flow. PayFast may retain transaction data under its separate obligations. This implementation does not retain its own payment/audit rows after account deletion; confirm South African accounting, tax, and POPIA retention requirements and implement a documented, minimized/anonymized retention policy if required before launch.
4. Device coordinates are requested only while the app is in use. Compass readings and manual coordinates are processed/stored locally and are not sent to the API. Manual coordinates are persisted in platform app preferences for convenience, until cleared or the app account is deleted.
5. `privacy_notice_accepted: true` is written to Supabase Auth user metadata on sign-up. A server-side acceptance timestamp/version and formal privacy-policy URL have not been added; supply the approved notice/version and retention evidence process before release.

## Geomagnetism and sensors

6. WMM2025 uses NOAA/NCEI's official degree/order-12 coefficients, WGS-84 geodetic coordinates, height in kilometres above the ellipsoid, epoch 2025.0, and linear secular change. The canonical <https://www.ncei.noaa.gov/sites/default/files/2025-02/WMM2025_TEST_VALUES.txt> file was fetched and its 12 published declination vectors match the test cases within the declared 0.1° tolerance. Values outside 2025.0–2030.0 are still calculated but marked expired/advisory; NOAA/NCEI's validity endpoint is 2030.0 (31 December 2029).
7. WMM declination is east-positive. Therefore `true heading = magnetic heading + declination` and `magnetic bearing = true bearing - declination`.
8. Native `flutter_compass` and iOS `webkitCompassHeading` are treated as magnetic. Absolute web-orientation headings are treated as magnetic for this product; browser implementations may differ and require physical-device validation. GPS course is true-north referenced. A GPS heading accuracy at or below 30°, a reported position accuracy at or below 50 m, speed above 1 m/s, or at least 10 m between accurate fixes is required to accept a GPS course. These cutoffs are product defaults, not guarantees supplied by the OS.
9. The native orientation adapter maps landscape-left to +90°, landscape-right to -90°, and upside-down portrait to 180°; heading correction subtracts that display rotation. OEM/plugin sensor orientation can vary; validate portrait and both landscape directions on representative iOS and Android hardware.
10. The app requests a GPS fallback after two seconds without a usable first sensor reading, three consecutive empty readings, or a zero/stuck sensor stream for three seconds; it retries the sensor every 60 seconds. A displayed reading becomes stale after five seconds without an update. These intervals are tunable service defaults and should be field-tested.
11. Web compass and geolocation require a secure context. Where `DeviceOrientationEvent.requestPermission` exists, the app calls it only from the user's Enable compass action. iOS/browser permission denial or unsupported hardware falls back to GPS when available; the UI also provides manual coordinates.

## PayFast

12. The implementation follows PayFast's current custom-integration and recurring-billing documentation at <https://developers.payfast.co.za/documentation/> (checked 2026-10-03): `subscription_type=1`, `frequency=3` (monthly), `cycles=0` (indefinite), `recurring_amount=100.00`, and an ISO `billing_date`. PayFast documents that `amount=0.00` can set up a free first subscription period without charging while collecting card details and 3-D Secure. A sandbox/live merchant test is still required before production.
13. The seven-day initial period is calculated from the member's UTC `trial_ends_at`; an already-expired trial uses the UTC checkout date rather than a backdated date. Confirm with the merchant account how a PayFast free-trial/zero-initial-amount event is delivered. The current handler expects a signed ITN with `payment_status=COMPLETE` and `amount_gross=0.00` to record trial setup; it does not process PayFast's separate optional `subscription.free-trial` JSON webhook.
14. Current PayFast recurring docs describe `COMPLETE`/`CANCELLED` transaction ITNs and separate free-trial webhooks. The handler also records `FAILED` and `PENDING` form ITNs without granting access, defensively; unknown statuses are rejected. Only `COMPLETE` at exactly R0.00 (initial setup) or R100.00 (renewal) changes entitlement. `CANCELLED` marks the subscription cancelled but preserves already-paid access until its entitlement period/grace ends.
15. Signature calculation uses the submitted field order, omits blank values, trims values, encodes UTF-8 with form rules (`+` for spaces, uppercase percent hex), appends the URL-encoded passphrase, and hashes with MD5. ITN order is preserved and `signature` must be the final field. This follows PayFast's custom integration example; verify against a sandbox ITN before launch.
16. PayFast's developer documentation currently publishes ITN sources `197.97.145.144/28`, `41.74.179.192/27`, `102.216.36.0/28`, `102.216.36.128/28`, and `144.126.193.139/32`. Refresh the list from the official page before launch. Forwarded IPs are honored only if the direct peer matches configured trusted-proxy CIDRs. Confirm the actual Cloud Run ingress/network path and restrict direct service access so a caller cannot bypass this policy.
17. ITN validation POSTs the ordered form fields (without the signature field) to the sandbox/live `/eng/query/validate` endpoint and requires literal `VALID`. Syntactically valid forms receive HTTP 200 after bounded verification/processing to prevent PayFast retries; malformed forms/content types receive 400/415.
18. **Merchant key exposure:** PayFast's documented custom HTML checkout requires `merchant_key` as a hidden form field; the app receives the short-lived checkout fields from the authenticated API and posts them to PayFast. This credential is therefore inspectable during checkout even though it is never a Flutter build define. The PayFast passphrase, Supabase service-role key, JWT secret, and other server secrets stay on the API. Confirm with the merchant whether the documented merchant key is considered publishable; if it must remain confidential, use a PayFast-supported server/hosted flow that does not expose it rather than this custom form.

## Platforms, subscriptions, and policy

19. The subscription product is one R100 ZAR monthly renewal after a seven-day no-charge trial. Calendar-month entitlement renewal clamps at shorter month ends. The three-day grace window is inclusive through `paid_through + 3 days`.
20. **Store review risk:** the product unlocks digital functionality. Apple Guideline 3.1.1 generally requires In-App Purchase, with region/program-specific exceptions; Google Play generally requires Play Billing unless an applicable, enrolled program applies. `STORE_BUILD=true` removes the PayFast checkout route from use and hides all PayFast prices and external purchase links. It does not yet implement StoreKit/Play Billing; a store build is therefore not ready for store submission until the correct native billing flow and policy eligibility are resolved. Do not infer worldwide approval from hiding the web checkout.
21. The app supports iOS/Android/Web source and PWA configuration. Android/iOS project-level files are included, but their generated build wrappers/Xcode project should be validated with the pinned Flutter toolchain on macOS/Android CI before release.
22. Cloud Run is the primary backend target in `africa-south1`; runtime secrets are injected from Secret Manager. Fly.io and Render can host the same Docker image. Vercel is permitted only for static Flutter web output, never as a Dart API host.
23. `Clock` is injected in core/API entitlement and billing calculations. Production uses UTC. The API currently verifies Supabase HS256 JWTs. If the project switches to asymmetric signing, implement JWKS validation before deployment; the server fails closed rather than accepting a different algorithm.
24. The API's rate limiter is in-memory per Cloud Run instance. Restrict ingress and add Cloud Armor or a shared rate-limit store for high-volume production use.
